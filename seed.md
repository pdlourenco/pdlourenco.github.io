# CLAUDE.md — pdlourenco.github.io

Personal academic + personal-interest website for **Pedro Lourenço**, built on [al-folio](https://github.com/alshedivat/al-folio) (Jekyll). Content is authored in a **Logseq graph**, exported by a **companion plugin**, and transformed into al-folio's data formats by scripts that live *in this repo*.

## Companion repos

| Repo | Role |
|---|---|
| `github.com/pdlourenco/logseq-alfolio-export` | Logseq plugin. Reads the graph, writes neutral intermediate YAML. |
| This repo | Consumes that YAML, transforms to al-folio formats, builds, deploys. |
| Logseq graph (local, not a repo) | Source of truth for CV, students, projects, personal pages. |

**Division of labour — do not blur this line:**
- The plugin knows about **Logseq** (namespaces, `[[refs]]`, properties, aliases). It knows nothing about al-folio.
- This repo knows about **al-folio** (RenderCV schema, collections, Liquid). It knows nothing about Logseq.
- The contract between them is the **intermediate YAML** (`cv.yml`, `profile.yml`, `personal.yml`, `publication_overrides.yml`, `manifest.json`). Treat it as a versioned API.

**Deliberate choices:**

- "Personal" is a first-class nav item. This is the site's distinguishing feature — do not treat it as an afterthought.

## Data pipeline

```
Logseq graph
    │  (plugin, on graph load or manual trigger)
    ▼
<graph>/assets/storages/logseq-alfolio-export/_logseq_export/
    ├── cv.yml                    ← neutral intermediate format
    ├── profile.yml
    ├── personal.yml
    ├── publication_overrides.yml
    ├── manifest.json
    └── blog/*.md
    │  (sync.sh from plugin repo, or manual copy)
    ▼
this repo: _incoming/           ← raw intermediate YAML, committed
    │  (bin/transform.py — YOU BUILD THIS)
    ▼
_data/cv.yml            (RenderCV schema)
_data/socials.yml       (from profile.yml)
_data/personal.yml      (custom, for the Personal page)
_data/coauthors.yml     (optional: from Logseq person pages)
_bibliography/papers.bib (Zotero + merged overrides)
_projects/*.md          (if using the collection)
_teachings/*.md         (if using the collection)
_posts/*.md             (blog)
    │  (GitHub Actions)
    ▼
GitHub Pages
```

**Why the `_incoming/` staging directory:** it makes the transform reproducible and diffable. You can re-run the transform without re-running Logseq, and `git diff` on `_incoming/` shows exactly what changed in the graph.

## Your main task: `bin/transform.py`

Reads `_incoming/*.yml`, writes al-folio native formats. Requirements:

### General
- Idempotent. Running twice produces identical output.
- Never destroys hand-written content. Files it owns get a header comment: `# GENERATED by bin/transform.py from _incoming/ — do not edit by hand`.
- Fails loudly on schema mismatch rather than silently producing half-empty YAML.
- Has a `--check` mode for CI that verifies output is up to date with input.

### `_data/cv.yml` (RenderCV)
Map intermediate → RenderCV. Expected shape (**verify first**):

```yaml
cv:
  name: Pedro Lourenço
  location: Lisbon, Portugal
  email: ...
  social_networks:
    - network: LinkedIn
      username: pdlourenco
  sections:
    experience: [...]
    education: [...]
    projects: [...]
    teaching: [...]
    awards: [...]
    skills: [...]
    research_interests: [...]
    languages: [...]
```

Notes:
- RenderCV expects `start_date` / `end_date` in `YYYY-MM-DD`, `YYYY-MM`, or `YYYY`. The intermediate format already uses hyphens (`2022-07`). Ongoing entries use `end_date: present`.
- RenderCV has a fixed set of *entry types* (`ExperienceEntry`, `EducationEntry`, `NormalEntry`, `OneLineEntry`, `BulletEntry`, `TextEntry`). Custom sections like "Supervised Students" must pick one that fits — likely `NormalEntry` (name + date + highlights) or `ExperienceEntry`.
- If RenderCV's schema can't express something (e.g. supervisor affiliations), put it in `highlights` as markdown rather than inventing keys — RenderCV validates strictly and invalid keys break PDF generation.
- If PDF generation via `.github/workflows/render-cv.yml` is enabled, a schema violation fails the build. Test with `rendercv render _data/cv.yml` locally.

### `_data/socials.yml`
From `profile.yml`. Each entry follows `jekyll-socials` conventions. Order in the file = display order. Verify supported network keys against the plugin's docs — unknown networks are silently dropped.

### `_data/personal.yml` + `_pages/personal.md`
No al-folio precedent for this page. You are building it.
- Custom layout override at `_layouts/personal.liquid` (or reuse `page` with includes).
- Sections: Music, Cycling & Hiking, DIY, Reading.
- **Music**: Spotify album embed (iframe, `open.spotify.com/embed/album/{id}`), SoundCloud profile embed, instrument list, band links (Rainy Days: Spotify/Bandcamp/SoundCloud).
- **Cycling & Hiking**: Wikiloc profile link. Wikiloc has **no official embed API** — check whether their per-trail iframe embed still works; if not, fall back to a link + static map image. Featured trips link to project pages.
- **DIY**: tool list, interest list, project cards with photo galleries (use al-folio's existing gallery/lightbox support — `images: lightbox2: true`).
- **Reading**: Goodreads profile `7400919-pedro`. ⚠️ The Goodreads API was retired to new keys in 2020; RSS feeds (`goodreads.com/review/list_rss/{id}`) still work but are unreliable. **Strongly consider using al-folio's native `_books/` collection instead** — it exists, has a `book-review` layout and a bookshelf page, and doesn't depend on a third party. Decide this explicitly and record the decision.

### `_bibliography/papers.bib`
- Source: Zotero + Better BibTeX auto-export straight into this path.
- `publication_overrides.yml` supplies `selected`, `abbr`, `preview` per cite-key.
- These are **BibTeX fields in al-folio**, not separate data. The transform must **merge them into the .bib entries**, not write a sidecar file.
- Merge must be non-destructive: parse the .bib, add/update only the override fields, preserve everything else and the entry order.
- `preview` images live in `assets/img/publication_preview/`.
- `abbr` values can link out via `_data/venues.yml`.

### `_data/coauthors.yml` (optional, high value)
al-folio auto-links co-author names in the bibliography from this file. Logseq already has person pages with affiliations. Generating this from the graph is nearly free and makes the publications page much richer. Keys must be **lowercase, unaccented last names**.

## Deployment

al-folio ships GitHub Actions workflows. Add the transform as a step, or run it locally and commit output. **Prefer running it in CI** with `--check` on PRs and a real run on `main`, so the repo can't drift from `_incoming/`.

Order matters: transform → RenderCV PDF → Jekyll build → deploy.

## Conventions in the intermediate format

You'll receive these already normalized by the plugin — do not re-implement:
- All `[[page refs]]` stripped and resolved to canonical page names (aliases expanded).
- Dates converted from Logseq `YYYY/MM/DD` to `YYYY-MM-DD`.
- Icons resolved from organization pages to short keys (`gmv`, `ist`).
- Supervisor affiliations already annotated where they differ from the student's university: `"Prof. Bruno J. Guerreiro (NOVA FCT)"`.

You **do** need to handle:
- Icon short keys → asset paths. Create `_data/icon_map.yml` and the actual SVG/PNG files under `assets/img/logos/`. This is manual work; no automation exists.
- Null/missing fields. The intermediate YAML omits empty properties entirely.
- Sort order (RenderCV renders in array order; sort experience/education reverse-chronologically, projects by `importance`).
